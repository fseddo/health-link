# Backend rules

This file extends the repo-root `CLAUDE.md` with rules that apply specifically when working under `backend/`. Read the root `CLAUDE.md`, `docs/SCHEMA.md`, and `docs/DECISIONS.md` for cross-cutting context before changing backend code.

## Project structure

```
backend/
├── app/
│   ├── api/v1/         # FastAPI routers (one file per resource: auth.py, workouts.py, …)
│   ├── core/           # config, security, JWT, password hashing
│   ├── db/             # SQLAlchemy models, async session, Base
│   ├── schemas/        # Pydantic v2 request/response models
│   ├── services/       # business logic — no FastAPI imports in here
│   └── main.py         # FastAPI app factory + router includes
├── alembic/            # migrations (autogenerated, reviewed by hand)
├── ml/                 # training, prediction, eval (added Phase 2+)
├── evals/              # LLM eval suites (Phase 4+)
├── prompts/            # LLM prompts as text (Phase 4+)
├── tests/              # pytest tests, mirrors app/ layout
├── docs/               # backend-specific architecture/feature docs
├── docker-compose.yml
├── Dockerfile
└── pyproject.toml      # uv-managed
```

Keep this layout. Files added in non-obvious places should be flagged in the PR description / commit message.

## Layered architecture rules

- **Routers (`app/api/v1/`)** validate input, call services, serialize output. **No business logic in routers.** No direct DB queries — go through services.
- **Services (`app/services/`)** contain all business logic and DB queries. They take a session via parameter, never import `Depends`, never import FastAPI. This makes them testable without spinning up the app.
- **Schemas (`app/schemas/`)** are Pydantic v2 only. Use `ConfigDict`, `field_validator`, `model_validator`. Do not use Pydantic v1 idioms (`Config` class, `root_validator`, etc.).
- **Models (`app/db/`)** are SQLAlchemy 2.0 declarative with `Mapped[]` and `mapped_column()`. No legacy `Column()`-on-class style. Use `AsyncSession` everywhere; no sync sessions.
- **Core (`app/core/`)** is for cross-cutting infra: settings, JWT, password hashing, dependency providers. No domain logic here.

## Conventions

### Sessions and DI
- DB session is injected via `Depends(get_db)` — never module-global, never imported into services as a global.
- Services accept `session: AsyncSession` as their first argument.
- Current user is a dependency (`Depends(get_current_user)`) on protected routes. Never read user identity from anywhere else in the request handler.

### Errors
- Services raise typed domain exceptions defined in `app/core/exceptions.py` (e.g. `NotFoundError`, `ConflictError`, `UnauthorizedError`).
- An exception handler in `app/main.py` maps domain exceptions to HTTP responses. Routers do **not** raise `HTTPException` directly except for genuinely HTTP-layer concerns (e.g. malformed token in a dependency).
- Never return a 200 with an error in the body. Use the right status code.

### Pydantic and units
- API-layer schemas convert between canonical (kg/m/s/cm) and display (lbs / per-user preference) at serialize time. Internal SQLAlchemy models and services see only canonical units.
- Conversion logic lives in `app/schemas/units.py` (or similar) and is shared across schemas — do not inline conversion factors.

### Migrations
- Run `alembic revision --autogenerate -m "..."` then **review and edit the migration by hand** before committing. Autogenerate misses things (enum changes, index renames, etc.).
- Never edit a migration that has been applied to a shared environment. Add a new migration instead.
- Migrations live in `alembic/versions/`. Each migration must be reversible (implement `downgrade()`).

### Logging
- Use the stdlib `logging` module via `logger = logging.getLogger(__name__)`. No `print()` in committed code.
- Log at info for state changes, warning for recoverable issues, error for bugs/unexpected failures. Never log passwords, tokens, or PII.

### Tests
- Pytest + pytest-asyncio + httpx.AsyncClient. Test layout mirrors `app/`.
- Every router endpoint has at least one happy-path test and at least one error-path test (auth missing, validation failure, not found, conflict — whichever apply).
- Every service function with a branch has tests for each branch.
- Use a transactional fixture that rolls back after each test. Tests must not leak state.
- Factories for test data live in `tests/factories.py`. Don't hand-roll fixtures in individual test files.

## Running things

- All tooling runs via `uv` inside Docker. The host needs only Docker.
- Dev: `docker compose up` brings up Postgres + API with live reload.
- Tests: `docker compose exec api uv run pytest`.
- Migrations: `docker compose exec api uv run alembic upgrade head` / `... revision --autogenerate`.
- Add make targets (`make up`, `make test`, `make migrate`) as the surface grows.

## Dependencies

- Adding a dependency to `pyproject.toml` requires a one-line justification in the commit message. If the dep replaces something we already have, say so.
- **No LangChain** — explicitly ruled out by ADR-003 (`docs/DECISIONS.md`). The rationale is that abstractions hide the mechanics, and learning the mechanics is the project's primary goal.
- **Other LLM framework abstractions** (LiteLLM, LlamaIndex, Haystack, etc.) are not blanket-banned but require a new ADR before adding, because they trip the same "hide the mechanics" concern. The Phase 4 LLM-provider ADR will likely settle this question once a provider is chosen — until then, default to raw provider SDKs.
- Pin Python to 3.12+ in `pyproject.toml`. Pin major versions of runtime deps; let minor/patch float.

## Backend docs (`backend/docs/`)

Architecture/feature docs specific to the backend go here. Examples of what belongs:
- `auth.md` — JWT structure, refresh-token rotation, password policy
- `database.md` — session management, migration workflow, transactional patterns
- `api-conventions.md` — error format, pagination, idempotency
- `testing.md` — fixture patterns, factories, async test gotchas

When you change auth, the DB layer, or an API convention, update the relevant doc **in the same commit**. Missing/stale docs are a blocker per `/dual-review` rules.

## Before committing

Run `/dual-review` on any change that touches more than a trivial bit (new endpoint, new model, new migration, new service, schema change, dependency change). Fix what comes back before committing. The two-pass review treats missing tests and stale docs as hard blockers, so address those before invoking it to avoid wasted cycles.
