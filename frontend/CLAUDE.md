# Frontend rules

This file extends the repo-root `CLAUDE.md` with rules that apply specifically when working under `frontend/`. Read the root `CLAUDE.md` first.

## What this frontend is for

The web frontend is **disposable**. It exists so the developer can click through backend features during Phase 1–2 development. iOS is the real client (Phase 3+). When in doubt between "polish the frontend" and "do nothing," do nothing.

## What this frontend is NOT for

- Not for end users.
- Not for design polish, animations, branding, dark mode, responsive layout, accessibility audits, or any UX work beyond "the buttons work."
- Not for automated tests. **Do not write frontend tests.** Backend and ML get tests; frontend gets manual clicking.
- Not for state management libraries beyond TanStack Query. No Redux, no Zustand, no Jotai, no MobX.

If you find yourself writing CSS overrides, custom theme tokens, transition animations, or anything that feels like "making it nice" — stop, you're doing the wrong thing.

## Stack

- Vite + React + TypeScript
- Tailwind + shadcn/ui (use the defaults; don't customize the theme)
- TanStack Query for server state
- React Router for routing
- `openapi-typescript` for generated API types — types are committed at `src/api/schema.gen.ts` and regenerated whenever the backend OpenAPI changes

## Project structure (target)

```
frontend/
├── src/
│   ├── api/            # generated types + a thin fetch client
│   ├── components/     # shadcn/ui components (mostly auto-generated by shadcn add) + a few app components
│   ├── pages/          # one component per route, self-contained where possible

│   ├── App.tsx

```

## Conventions

### State
- **Server state**: TanStack Query. Every API call goes through a `useQuery` / `useMutation` hook in or next to the page that uses it. Don't share query hooks broadly until there are 3+ call sites.
- **Local UI state**: `useState` in the component that owns it. Lift only when needed.
- **Global state**: avoid. If you think you need it, you don't — the backend is the source of truth.

### API client
- **Always** use the generated types from `src/api/schema.gen.ts`. Never hand-write request or response types.
- The fetch wrapper attaches the access token from Keychain-equivalent storage (just localStorage for this throwaway frontend) and handles 401 → refresh.
- Regenerate types after backend OpenAPI changes: `npm run gen:api` (or whatever target we define).

### Units and display
- The backend converts to display units (lbs / kg) based on `users.weight_unit_preference`. The frontend displays what it receives. **Do not convert units in the frontend.**
- If the displayed unit needs to change, the user updates their preference via `PATCH /api/v1/me` and the backend starts returning the new unit on subsequent requests.

### Auth
- Tokens in localStorage (this frontend is dev-only — Keychain-equivalent security is iOS's problem).
- Access token in memory + localStorage; refresh token in localStorage with the access token.
- 401 → call `/auth/refresh` once → retry the original request. If refresh fails, redirect to login.

### Styling
- Tailwind utility classes inline. shadcn/ui components imported as-is. No custom theme. No global CSS beyond `index.css` (Tailwind directives + maybe one or two resets).
- No animations. No transitions other than what shadcn ships by default.

### Dependencies
- Adding a dependency requires a one-line justification. If a problem can be solved by writing 20 lines of code instead of adding a dep, write the code.

## Frontend docs (`frontend/docs/`)

Frontend-specific notes go here. Examples:
- `api-codegen.md` — how to regenerate types from the backend OpenAPI
- `query-patterns.md` — TanStack Query conventions used in this app
- `auth-flow.md` — token storage and refresh flow

Keep these short. The frontend is throwaway, so docs about it are throwaway too — write only what's needed to ramp a new contributor (or future-you) in 5 minutes.

## Before committing

Run `/dual-review` on non-trivial frontend changes. The reviewer applies the rules above — expect blockers on: hand-written API types, frontend tests (yes, *adding* them is the violation), custom theme work, new state-management deps, doc updates missed.
